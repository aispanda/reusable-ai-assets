# Reuse prompts and release handoff

## Start in another thread or compatible IDE

> Use $deliver-blog-community from the supplied asset location to add the approved
> login, comments, role requests, authoring and publishing capability to this site.
> First inspect the site's existing implementation and validate the consumer profile.
> Report missing runtime, policy, authority or compatibility prerequisites before
> mutation. Reuse packaged code/tests; do not regenerate a CMS from this prompt.
> Work on the linked story branch. Use one lead and an independent verifier only
> when useful. Preserve existing users/content. Run the risk-relevant scenario IDs,
> install the exact archive via scripts/package.mjs using its supplied SHA-256,
> keep my site profile outside installed core, and consult references/runtime.md,
> then deploy to isolated staging only within the supplied authorization.
> Return the exact URL, version, evidence and remaining blockers. Never promote
> production from a draft package or an unexecuted test plan.

If skill discovery is unavailable, read this package's SKILL.md by its actual path
and follow the same workflow. The prompt does not install tools or grant authority.

## Verify a second site

> Verify this installed capability against assets/scenarios.json on the supplied
> second-site staging URL. Use the declared disposable identities and cleanup ledger.
> Compare every scenario ID with the consumer's Linear contract and packaged
> executable test mapping. Report PASS/FAIL/UNPROVEN for the exact image and site.
> Classify tooling failures separately. Do not alter the source site's data or
> weaken assertions. Stop production promotion on missing required evidence.

## Bounded defect repair

> Fix only the reproduced scenario failures in the supplied evidence on this story
> branch. Preserve the reusable core/profile boundary. Add a regression test, rerun
> affected tests, then obtain independent verification. Do not patch production
> directly, make unrelated infrastructure changes, or launch broad research.

## URLs and handoff packet

The consumer's private handoff must contain the actual:
- story and test-contract document links;
- reviewed source commit/PR and released package location/version;
- second-site staging URL and representative disposable article URL;
- CI/test evidence and cleanup result;
- production URL only after authorized promotion.

Do not invent a staging URL or call a local worktree a released asset. Missing URLs
are named prerequisites. Keep live project links and accounts out of this package.

## Promotion sequence

Source fixes verified → versioned runtime extracted → second-site staging installed
and tested → defects repaired in core with regressions → exact image promoted under
the consumer's release authority → asset release/registry publication approved.

Testing the asset on another site's staging before promoting that site is required
for the claimed portability. Installation/build and emulator tests in a clean
second local folder prove local integration, not live OAuth/browser/deployment.
