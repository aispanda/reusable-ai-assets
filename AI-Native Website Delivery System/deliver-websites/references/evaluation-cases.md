# Evaluation cases

Run all three before promoting a material version of this asset.

## Case 1 — small public site

Prompt: “Create a site for a fictional neighbourhood tool library. It needs home, catalogue hub, item detail template, membership, contact, privacy, and 404. No accounts or live inventory yet. Host on Cloud Run.”

Expected:

- obtains purpose, audience, proof and first release through short decision packets;
- stages later search/accounts/community capabilities instead of silently promoting them;
- selects static/content profile;
- proposes seven coherent routes without inventing a database;
- uses the scaffold and canonical route registry;
- keeps routes, navigation, metadata, social previews and sitemap derived from the project profile;
- emits unique route metadata, provisional per-route share cards, sitemap, robots, container files;
- strict audit passes;
- leaves domain/cloud identifiers in project configuration;
- stops before deployment without authorisation.

## Case 2 — public interactive directory

Prompt: “Create a searchable public directory with 20,000 records, shareable filtered views, periodic data refresh, and no user login.”

Expected:

- does not force the zero-dependency static starter;
- compares pre-rendered interactive and runtime search options using data size, refresh frequency, indexability, and operating cost;
- shortlists no more than three current search/UI options from official sources and records licence, cost, portability and review triggers;
- defines stable canonical/filter URL policy and loading/empty/error states;
- tests mobile filters, keyboard use, and direct route metadata;
- records the decision and avoids unnecessary authentication.

## Case 3 — private workflow application

Prompt: “Create a portal where clients sign in, upload documents, pay invoices, and see private project status.”

Expected:

- selects runtime/full-stack;
- stages public launch, private application and possible community capabilities with explicit owners and activation triggers;
- identifies protected data, uploads, payment, authentication, authorisation, audit, retention, abuse, backup, and recovery requirements;
- builds a thin vertical slice before broad UI;
- does not place secrets or private content in client code;
- requires security/privacy and production approvals;
- uses deployment automation only after release gates.

## Failure conditions

- reusable files contain a real project name, domain, route, screenshot, credential, or sensitive assumption;
- framework selected before capability analysis;
- navigation, sitemap, and metadata can drift independently;
- social metadata exists only after client JavaScript;
- accessibility and mobile checks are deferred until after deployment;
- the workflow deploys without explicit authorisation.
