# Issue-resolution patterns

Log only failures, ambiguities or repeated work that could recur across projects. Do not log routine commands. Each pattern must state the observable symptom, root cause, smallest safe resolution and a prevention check.

| ID | Symptom | Root cause | Reusable resolution | Prevention / automation | Seen |
|---|---|---|---|---|---|
| WEB-001 | Package install/build fails because a dependency build script was ignored | Secure package managers require explicit approval for native/compiler post-install scripts | Inspect the dependency and allow-list only the exact required package; never enable all scripts globally | Pin package manager; commit its allow-list; verify clean install/build | Public website pilot, 2026-08-06 |
| WEB-002 | An embedded static tool loads its HTML but CSS/JS 404 beneath `/labs/...` | Its build uses root-absolute asset URLs | Build the tool with an explicit public base path, then validate emitted HTML before copying | Sync script rejects a build missing the expected base | Public website pilot, 2026-08-06 |
| WEB-003 | A reusable live tool risks becoming a divergent project copy | Viewer source and website release have different owners | Keep reusable source canonical; website tracks only a verified public artifact plus a deterministic sync command and provenance | Router names the source owner and generated destination | Public website pilot, 2026-08-06 |
| WEB-004 | Cloud deployment cannot proceed although the site is ready | Billing account is closed/inactive, requires activation, or authenticated identity is wrong | Keep build independent of deployment; preflight account, billing, project access and authenticated identity before release work | Deployment gate checks active billing, `gcloud` identity and project before image build | Public website pilot, 2026-08-06 |
| WEB-005 | Cloud configuration contains guessed or publicly exposed operational identity | Project, region, account and registry were not confirmed or were stored in public source | Require explicit project-owned values; keep personal account identity and secrets in local/private deployment configuration | Reject placeholders and secret-like/public identity values during release audit | Public website pilot, 2026-08-06 |
| WEB-006 | A new public site accidentally exposes a source project's brand, client or competitor terminology | Reused content, generated bundles or embedded tools crossed the project boundary | Define project-specific prohibited terms and scan both source and generated output; rewrite concepts generically rather than mechanically renaming protected copy | Make the boundary scan a production-build gate and exclude only dependencies/Git internals | Public website pilot, 2026-08-06 |
| WEB-007 | A generated sub-application works from `index.html` but its friendly directory URL returns 404 during framework development | The parent framework owns route resolution while the nested artifact is only a public file tree; development and web-server fallback rules differ | Link to the verified artifact entry file unless the parent explicitly owns a wrapper route; test both development and production-server routing | Route audit follows every live-demo link and verifies title/content, not status alone | Public website pilot, 2026-08-06 |
| WEB-008 | The static site builds, but its Cloud Run container cannot be tested locally | No local container engine is installed or available | Do not install infrastructure tooling implicitly; complete source/build/route checks locally, then use the approved cloud build service as the container-build gate | Release checklist records which environment verified the image and blocks deployment until build plus runtime probe pass | Public website pilot, 2026-08-06 |
| WEB-009 | A reusable test command fails because `python` or another expected command is not on `PATH` | The environment provides a bundled/runtime-specific executable rather than a global command | Resolve the approved project or workspace runtime once; do not install or substitute a new runtime automatically | Preflight reports resolved executable/version and examples say “configured runtime,” not a single assumed command name | Public website pilot, 2026-08-06 |
| WEB-010 | A public live demo exposes proprietary schema, sample records or internal product terminology even though its source is ignored | Browser-delivered JavaScript/data must be downloadable to run; `.gitignore` and container exclusions do not protect public runtime assets | Publish a deliberately sanitized fictional fixture, or obtain explicit approval that the full artifact is public; keep the canonical private source outside the public build | Release audit scans embedded bundles and records a public-data approval for every live tool | Public website pilot, 2026-08-06 |
| WEB-011 | Cloud commands target the wrong project although the operator signed in with the intended account | Authentication identity and active CLI project are independent settings; a previous project remained selected | Verify account and project separately, then pass the project explicitly to every mutating command | Preflight compares expected account/project with CLI values and stops on either mismatch | Public website pilot, 2026-08-06 |
| WEB-012 | Cloud build cannot start even though the runtime API is enabled | First deployment also needs the build API and image registry; runtime readiness alone is insufficient | Inventory and verify every required API and repository before submitting a build; enable or create only with explicit deployment authority | First-deploy preflight checks billing, build API, runtime API, registry API and target repository | Public website pilot, 2026-08-06 |
| WEB-013 | A reusable shell deployment script cannot run on Windows although Git is installed | The compatible shell executable exists but is absent from `PATH` | Resolve and invoke the approved shell by its exact path; do not install or substitute tooling automatically | Runtime preflight reports the executable path and version before the deployment gate | Public website pilot, 2026-08-06 |
| WEB-014 | Repeat-deployment automation is blocked on a brand-new service because the service URL, registry or cloud resources do not yet exist | Bootstrap deployment and routine releases have different prerequisites and risk | Separate an explicit, idempotent bootstrap stage from the immutable repeat-release path; record every created resource | Handoff declares `first deployment` or `repeat release` and validates the matching checklist | Public website pilot, 2026-08-06 |
| WEB-015 | Deployment is authorised, but the approved automation refuses a dirty or unpushed source tree | Production approval does not automatically grant permission to commit or publish source; the release tool requires a traceable remote revision | Keep source-publication approval and production-deployment approval as separate gates; deploy only an identified remote revision | Release record captures repository, revision, visibility, source approver and deployment approver | Public website pilot, 2026-08-06 |
| WEB-016 | A public commit would carry an unrelated personal or prior-project author identity | Git inherited global author settings that were never checked against the repository's public identity and privacy policy | Verify author name/email before staging; set a repository-local, privacy-safe identity when the project owner approves it | Public-source gate records repository visibility and the exact commit author identity before commit | Public website pilot, 2026-08-06 |
| WEB-017 | Diagram relationships are technically present but hard to follow at fit-to-view scale | Connector strokes and endpoint markers were too thin and too close to the canvas tone | Use a high-contrast relationship token with visibly heavier normal, selected and path states; verify at the default fitted zoom | Visual gate checks connector contrast, multiplicity markers and selected-path emphasis at representative zoom levels | Public website pilot, 2026-08-06 |
| WEB-018 | A visitor opening an embedded tool cannot find the host site's navigation | The tool is served as an independent static application, outside the host page layout | Give public builds an optional, always-visible host return link configured at build time; avoid hardcoding the consuming brand into reusable source | Route audit enters every standalone tool and verifies a visible keyboard-accessible return path | Public website pilot, 2026-08-06 |
| WEB-019 | An action link appears clickable but nothing meaningful happens | The link targets its own already-active page anchor and no hidden content, focus or state changes | Give every action a real destination or observable interaction; render unavailable items as labelled non-actions | Route audit rejects self-referential links unless activation produces a verified URL, focus, visibility or state change | Public website pilot, 2026-08-06 |
| WEB-020 | A public asset catalogue silently omits valid assets or misstates maturity | The website catalogue and canonical asset inventory are maintained independently | Reconcile the public catalogue against the canonical inventory, preserve honest statuses and publish only deliberately excluded items through an explicit rule | Release audit compares stable asset IDs, destinations and statuses with the approved publication inventory | Public website pilot, 2026-08-06 |
| WEB-021 | A public-source push fails with HTTP 403 although author identity and target remote look correct | Git commit identity and cached remote credentials are independent; the credential belonged to another account | Verify the authenticated Git principal and repository write access before committing; switch accounts through the approved credential manager, never by embedding a token | Public-source gate records remote URL, visibility, commit author and authenticated principal separately | Public website pilot, 2026-08-06 |
| WEB-022 | A valid site build fails while refreshing framework-generated files | The managed execution identity can read the project but cannot write its generated workspace directory | Confirm the target paths, then rerun the same verified build with narrowly approved workspace write access; do not change tooling or install replacements | Build preflight verifies write access to framework cache and output directories | Public website pilot, 2026-08-06 |
| WEB-023 | First deployment reaches release time with a different CLI default project, missing build API/repository/service and no runtime URL | Repeat-release assumptions were checked too late and the runtime origin did not exist yet | Classify first versus repeat release before approval; use explicit project flags, verify billing/APIs/repository, and resolve the Cloud Run URL after the first build instead of guessing | Website handoff and deployment preflight perform the same readiness classification before cloud mutation | Public website pilot, 2026-08-06 |
| WEB-024 | Local build passes but the clean container install rejects a recently published, reviewed dependency | The Docker build copied the manifest and lockfile but not the package-manager policy file containing the exact release-age exception | Copy every package-manager policy file before dependency installation; keep the age rule enabled and allow only the reviewed package/version | Container review checks the files available at the install layer; first deployment uses a clean container build as the release gate | Public website pilot, 2026-08-07 |
| WEB-025 | Cloud deployment succeeds but an anonymous visitor receives HTTP 403 | The build principal created the service but could not apply the intended public invoker policy | Apply the separately approved public/private access policy with an authorised principal and verify without credentials | Release readiness records access mode and performs an anonymous request after deployment | Public website pilot, 2026-08-07 |
| WEB-026 | Release verifier fails because a successful builder no longer prints a legacy tagging phrase | Mutable console wording was treated as authoritative evidence | Use Cloud Build status, immutable registry digest, serving-revision digest and traffic allocation; keep log phrases diagnostic only | Verification relies on structured cloud state rather than presentation text | Public website pilot, 2026-08-07 |
| WEB-027 | A healthy new service returns one transient 503 immediately after becoming public | Runtime readiness briefly lagged the ready control-plane state | Retry only transient HTTP failures with a small bounded delay; still require final HTTP 200 | Post-release checks use bounded retries and record persistent failures as defects | Public website pilot, 2026-08-07 |
| WEB-028 | Longread heading looks much narrower than the page / body; large empty space beside the title | Intro sat in a full `shell` while the article used TOC+column, and/or heading `max-width` (e.g. `18ch`) was far tighter than body measure | Put intro and article on the same grid/content column; let the column set measure—do not cap headings much narrower than body unless a pull-quote | Human gate: compare intro heading and first body block inline-start + width; document in `single-page-craft.md` | Principles longread, 2026-08-07 |
| WEB-029 | Desktop sticky TOC works but mobile readers cannot jump sections | TOC hidden or `position: static` with no collapsible jump control | Provide a mobile “On this page” control (`details`/drawer) under the header; keep heading IDs stable | Page-craft loop + quality gate: verify jump nav at ≤580px | Principles longread decision loop, 2026-08-07 |
| WEB-030 | In-page TOC jump lands with heading hidden under sticky header | Missing `scroll-margin-top` on section headings | Set `scroll-margin-top` ≥ sticky header height on target headings | Quality gate: deep-link each TOC anchor under sticky chrome | Principles longread decision loop, 2026-08-07 |

| WEB-031 | Google sign-in succeeds in staging but production reports an expired session; retry can remain disabled | Revoked-session verification requires runtime Firebase user-lookup IAM, which differed between environments; the server conflated service errors with invalid credentials and the UI relied on a fresh auth observer event | Keep revocation checks, verify `firebaseauth.users.get` independently for each target, classify unavailable verification as a service failure, and initialize an explicit sign-in result directly so same-account retry works | Blog [staging preflight](../../deliver-blog-community/runtime/tests/staging-preflight.mjs), HTTP authentication tests and sign-in navigation tests cover denied/unknown IAM, credential failures, service failure, retry and restoration without navigation | Second-site blog adoption, 2026-09-25 |

## Promotion rule

WEB-011 through WEB-015 are promoted into `cloud-run-handoff.md`; the public-source and release-evidence controls are also promoted into `quality-gates.md`.

When a pattern repeats or creates material risk, improve a checklist, validator, template or test—not just this table. Link the automation change from the pattern and verify it on a neutral fixture.
