# Build readiness and informed challenge

Read before substantive build or integration work. Prepare enough context and evidence for the next action; do not load every installed skill, clone every candidate repository, or turn readiness into a separate approval ceremony.

## Confirm the essentials

Keep a short readiness note in the existing task or project brief, covering:

- **Outcome:** the user goal, scope, exclusions, material constraints, current authorization, and observable acceptance checks.
- **Reuse:** existing local and open-source options considered, the chosen adopt/compose/adapt/build route, and the exact gap requiring new work. Reuse a prior assessment if its task, version, rights, and environment assumptions still hold.
- **Sources:** authoritative requirements, selected documentation and source locations, reviewed revisions, and missing or conflicting facts. Keep the brief a source-linked working view, not another system of record.
- **Capabilities:** relevant skill instructions actually read, intended repository/ref established, and required tools, accounts, runtimes, and permissions verified with a bounded read or smoke check. A skill name in a catalog is only discovery; a tool installed on disk is only availability.
- **People or agents:** the smallest useful role set, each role's responsibility, applicable skills, accessible evidence, permitted actions/paths, and expected handback.
- **Verification:** checks that can demonstrate completion, who will perform them, and any unresolved prerequisite that blocks the next action.

Read repository instructions before changing files. Load selected skill instructions and relevant source sections, or provide exact accessible locations with a requirement to read them before acting. When delegating, ask each agent to report material missing context or capabilities immediately; do not claim another agent loaded a resource just because it was sent a link.

Use the existing delivery owner for project readiness and authorization, and the existing orchestration owner for detailed dispatch, reviewer role cards, and repair limits. In this library those owners are RA-005 and RA-008, discovered through their records. Check the selected version and availability; do not link to an unmerged local worktree as a portable dependency or duplicate their templates here. If an owner's guidance conflicts with actual authority or observed evidence, report the conflict and use only a supported path.

## Distinguish research readiness from execution readiness

An agent with incomplete tooling may still contribute a source-grounded proposal. Missing runtime access must limit its execution claims, not automatically exclude its useful evidence from a comparison. Separate official documentation, implementation resources, and observed operation results.

Proceed with a build step when its required context, tools/access, reuse decision, acceptance checks, and authority are sufficient. Otherwise state the exact missing prerequisite, who can resolve it, and the next useful action; continue independent preparation. Do not claim an untested integration is ready because its documentation exists.

A delivery-specific requirement, such as a particular protocol or deployment surface, applies only when the task actually requires it. Do not turn one project's eligibility rule into a universal rule for assets or agents.

## Choose challenge proportional to uncertainty

| Situation | Useful approach |
|---|---|
| Routine change with clear acceptance checks | One implementer using existing checks; follow any required repository review. |
| Material architecture, reuse, security, or data-integrity uncertainty | A bounded independent challenger checks the evidence and identifies consequential gaps before the dependent build. |
| Independent research or implementation areas | Parallel specialists with distinct responsibilities and non-overlapping write scope. |
| Several plausible designs remain | Independently prepared alternatives under the same requirements, then an evidence-based comparison. |
| Complex completed artifact | An independent reviewer inspects the actual result and performs authorized checks. |

User-requested participation and review requirements still apply. If a broad contest is requested, retain the requested opportunity to contribute while focusing deep review on material differences; do not quietly exclude required participants to save effort.

Give a challenger the original goal, constraints, source evidence, and acceptance criteria before persuasive summaries from the builder. Ask for omissions, counterevidence, overlooked reusable options, and a practical check that could disprove the proposal. Findings should state evidence, impact, and the smallest useful action; "no material addition" is valid.

For a requested contest, use the available orchestration owner's review procedure and preserve the required participation. Record material changes and unresolved questions in the existing task evidence. Silence or no objection is not agreement; do not create a second debate protocol here.

Use a judge or reviewer only with explicit criteria and inspectable evidence. Favor reproducible checks over confidence scores, majority vote, or debate length. Label simulated product perspectives and model-only evaluations; they do not prove that a vendor, product, or integration supports the scenario. Request concise findings and source evidence, not private chain-of-thought.

When material disagreement persists, obtain the missing evidence or escalate the consequential decision. Never describe the best of several failed candidates as passing. Bound the review and repair effort by the task; do not restart endless debates or prescribe one team size for every build.

## Learn whether the method helped

Record the defects found, unnecessary implementation avoided, task outcome, and effort when assessing this approach. Compare with the previous or simpler workflow before claiming improvement. Remove review steps that add no observable value, while preserving required coverage and independence. Recheck readiness when scope, sources, dependencies, permissions, or delegated work change materially.
