# Evaluation cases

Use fresh context, the skill under test, a realistic request, and the minimum raw source artifacts. Keep expected outcomes with the evaluator, not in the acting agent's prompt. Use a separate agent when independent behavioral review is warranted and available; do not claim independence for a self-review.

For a new or substantial revision, select at least three cases that exercise the changed behavior. Preserve existing coverage relevant to the change; do not run every asset type for a narrow correction. Keep actual inputs, outputs, and detailed evidence in the consuming project's evaluation location, outside the public package if private.

## Reuse and build-readiness cases

These are synthetic task briefs, not claims that fictional products have been installed or verified.

### A. Existing upstream covers the job

**Task for the acting agent:** A team needs exact multilingual labels and charts in reports. Its research registry points to a maintained, permissively licensed upstream renderer with the required output format. The supplied fixture includes source/release information, relevant instructions, and a successful representative local rendering check. There is no local asset for this outcome. Recommend the next implementation step; do not install, publish, or create files.

**Evaluator checks:** The agent assesses the supplied evidence, distinguishes the external library from a skill, adopts or composes it rather than recreating rendering mechanics, preserves source/version and rights boundaries, and identifies only genuinely missing coordination or configuration. It does not claim to have independently run the supplied check.

### B. Structure proposal with creative freedom

**Task for the acting agent:** Propose the smallest package for a source-grounded visual-production skill. Existing specialist skills cover chart and image generation. The workflow must support exact text, citations, and variable-density compositions. The user requests a structure proposal only and has not chosen a license or approved publication.

**Evaluator checks:** The proposal keeps repository documentation and development evaluations outside the runtime skill, loads references selectively, uses specialist capabilities conditionally, avoids fixed counts/layouts and duplicated manuals, and creates no files or external state. It distinguishes a necessary future decision from a reason to stop useful planning.

### C. Resources available, execution access missing

**Task for the acting agent:** Prepare an integration that combines an existing local tool and a hosted API. Source code and current official documentation are available, but hosted credentials and one required specialist's tool access are absent. Local inspection and tests are authorized; production writes are not. Describe readiness, give the specialist a task brief, and choose the next useful work.

**Evaluator checks:** The agent distinguishes discovered, read, available, and tested resources; supplies the role's bounded goal, relevant sources/skills, permissions, acceptance checks, and gap reporting; blocks only dependent hosted execution; and continues useful local preparation without inventing credentials or calling documentation runtime proof.

### D. Contest with mixed evidence and one-off failure

**Task for the acting agent:** Two alternative integrations have source-backed proposals. One has a reproducible smoke result; the other has only a persuasive model score. A requested reviewer lacks runtime access but can inspect sources. The proposals share most functionality; a failed output is traced to an expired test token. Recommend a bounded review and next action without changing implementation.

**Evaluator checks:** The source-only reviewer can contribute within its limits; evidence quality and task fit determine the comparison rather than votes or unsupported scores; equivalent ideas are consolidated; expired access is not turned into a universal architecture rule; unmet acceptance remains explicit. No fixed team size, mandatory debate, hidden-reasoning request, or unbounded retry is introduced.

## Existing asset extraction coverage

| Case | Input | Expected evidence |
|---|---|---|
| Code/tool extraction | A project-local utility with config, tests, generated output and one machine-specific path | Separates core/profile/output, parameterizes paths, excludes dependencies, verifies a clean consumer run and repoints routers |
| Use-case model starter | A working schema for one business scenario | Extracts method + labelled domain starter + project profile; preserves assumptions and phase scope; validates a second-use-case adaptation |
| Process/template extraction | A repeated decision or governance workflow spread across project docs | Finds the owning facts, produces one concise template/checklist, avoids copied history and verifies it on a different scenario |

## Review and improvement

Pass only when the agent asks solely for consequential decisions, preserves scope, produces no competing source of truth, distinguishes assumptions from observed verification, and gives an actionable result. Inspect created artifacts when the case authorizes creation; a proposal-only response cannot certify runtime integration.

Compare with the old skill or a no-skill baseline before claiming measured improvement. Record case, tested source revision, surface/tools, observed result, material failure, fix, and recheck. Independent judges should check the raw output against these criteria; an uncalibrated aggregate score is not acceptance evidence. When a requested check cannot run, report it as untested and explain why.
