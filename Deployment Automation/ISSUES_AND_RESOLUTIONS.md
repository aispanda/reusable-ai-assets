# Deployment issues and resolutions

Record reusable root causes only. A resolution is complete when its prevention step is incorporated into the workflow or release checklist.

| ID | Symptom | Root cause | Resolution | Prevention |
|---|---|---|---|---|
| DA-001 | First release cannot build, push or resolve a service URL | Repeat-release assumptions hid missing APIs, image repository and service | Classify first deployment; verify billing/APIs/repository; resolve the runtime URL after deployment | Preflight checks first-deployment readiness before mutation |
| DA-002 | Local build passes but clean cloud container install rejects a dependency-age rule | The Docker install layer did not include the package-manager policy file | Copy all policy files before dependency installation; retain the rule and exclude only an explicitly reviewed package/version | Container review compares local and install-layer policy inputs |
| DA-003 | CLI default project differs from deployment target | Shared workstation retained another project's default | Pass the target project explicitly on every cloud command and show the mismatch as a warning | Preflight verifies access and billing against the configured target, not the global default |
| DA-004 | Deployment succeeds but the public URL returns 403 | The build principal created the service but could not apply unauthenticated invocation | Apply the approved public/private access policy with an authorised principal, then verify anonymously | Treat access mode as a separate release gate and test without credentials |
| DA-005 | Verifier reports failure although build, image digest and serving revision are correct | It depended on one legacy console phrase that newer builders omit | Treat log wording as diagnostic; verify build status, immutable registry digest, revision digest and traffic through APIs | Never use mutable console text as authoritative release evidence |
| DA-006 | A newly public healthy service returns one transient 503 during verification | First-request platform or instance readiness briefly lagged the ready control-plane state | Retry only transient HTTP failures with a small bounded delay, then fail loudly | Public-route checks use two bounded retries and still require final HTTP 200 |
| DA-007 | Custom domain work drifts toward ALB “because Google recommends it” and burns ~$18+/mo | Production guidance defaults to load balancer without a zero-cost mandate | Library policy: Cloud Run domain mapping only; ALB forbidden unless CD-B2 trigger + explicit cost acceptance | `CUSTOM_DOMAIN.md` policy table + `domain_map.sh` warns; backlog CD-B2 |
| DA-008 | Agents propose Firebase Hosting as domain front-door | Older docs list Firebase as a mapping option | Firebase proxy excluded by default (past delivery friction) | `CUSTOM_DOMAIN.md` forbidden list; backlog CD-B3 only if Firebase already mandated |
| DA-009 | Operators invent DNS records instead of using Google’s mapping output | Registrar UI is filled before `domain-mappings describe` | Always `--export-dns` → plan JSON → registrar apply | `export_dns_records.py` + `apply_dns.py`; never hand-author rrdata |
| DA-010 | Spaceship API DNS apply fails with auth/forbidden despite valid keys | API Manager IP allowlist does not include the agent/runner egress IP | Use `--provider manual` (UI paste from exported plan) until the IP is allowlisted; then retry API | Default DNS path is UI paste; document IP allowlist in `CUSTOM_DOMAIN.md` before recommending API |
| DA-011 | Only `www` or only apex is mapped; the other URL fails for visitors | Assumed one hostname is enough | Map **both** by default; set canonical to `www` | Defaults table in `CUSTOM_DOMAIN.md`; `CUSTOM_DOMAIN_HOSTS` lists both |
| DA-012 | `domain-mappings create` rejects hostname: domain not verified for account | Cloud Run mapping requires prior domain ownership proof (Search Console / `gcloud domains verify`) | Run `gcloud domains verify <apex>`; publish the TXT (or other) challenge at the registrar; re-run `--map` | Add ownership-verify as step 0 before `--map`; export challenge for UI paste |
| DA-013 | Exported mapping JSON on Windows is UTF-16 and breaks UTF-8 parsers | PowerShell `>` / default `Out-File` writes Unicode | Write plans via Python/`cmd` redirection or decode `utf-16`/`utf-8-sig` in exporters | `export_dns_records.py` should tolerate UTF-16 BOM when reading gcloud capture files |
| DA-014 | DNS correct and DomainRoutable but HTTPS fails briefly | Managed certificate still `CertificatePending` (minutes–hours) | Do not change mapping records; poll `domain-mappings describe` until Ready; keep `*.run.app` as fallback | After UI paste, treat cert wait as normal; only escalate if pending >24h with correct public DNS |
| DA-015 | Cert stays pending: “challenge data was not visible through the public internet” while public A/CNAME already match Google | Propagation lag, intermittent checker path, or registrar edge cache; Google lengthens retry (e.g. 15m) | Confirm NS + A/AAAA/CNAME via 8.8.8.8 and 1.1.1.1; do **not** rewrite correct records; wait for Retry; escalate only if still failing after several successful public resolutions and >2h | Document challenge-not-visible as wait/retry, not a signal to invent different IPs |
| DA-016 | Deploy succeeds but INFRA VERIFY fails with curl exit 28 / host`:8080` on Windows Git Bash | MSYS path conversion rewrites `https://…/route` during verify even when `MSYS2_ARG_CONV_EXCL` lists http/https | Call `curl.exe` when present; otherwise force `MSYS_NO_PATHCONV=1` and `MSYS2_ARG_CONV_EXCL='*'` for curl | `run_curl` in `deploy.sh` prefers `curl.exe` |
| DA-017 | Agent keeps re-asking the user to type `DEPLOY` after they already approved in the chat | Approval channel treated as “new terminal only” | Accept exact chat `DEPLOY` once for that SHA and relay LF-only stdin; do not ask again for the same release | `DEPLOY_PROJECT_PROMPT.md` one-approval rule |
| DA-018 | Windows operators cannot start the documented command because `bash` is not on PowerShell `PATH` even though Git Bash is installed | The operating guide assumed a POSIX shell command alias was globally available | Invoke the installed Git Bash executable explicitly and continue using the existing Windows path conversion | README includes the explicit Windows invocation fallback |
| DA-019 | The RA-002 test suite passes preflight gates, then exits during standalone verification on Windows | `deploy.sh` correctly prefers `curl.exe`, but the test fixture stubbed only `curl`, allowing the real network client to escape the isolated test | Create matching `curl` and `curl.exe` stubs in the temporary fixture | The test now proves native curl preference without making a network call |
| DA-020 | A caller reports a deployment timeout even though Cloud Build continues and succeeds | The calling tool allowed less time than combined preflight, upload, build, rollout and verification | Use a foreground timeout of at least 15 minutes; if the caller still exits after submission, reconcile the exact SHA in Cloud Build and Cloud Run before retrying | README retry safety requires sufficient caller time and exact SHA reconciliation after interrupted output |
| DA-021 | Git Bash reports a controller path ending at the first space, although the reusable asset exists | PowerShell and `bash -lc` consumed nested quotes before Bash parsed a POSIX path containing spaces | Escape spaces in the POSIX controller path, such as `Deployment\ Automation/deploy.sh`, while keeping the repository change and config assignment in the same command | README Windows guidance includes the proven escaped path form; run `--check` before opening the deployment gate |
| DA-022 | The approval gate receives `DEPLOYn` even though the caller attempted to send `DEPLOY` plus newline | A `\n` escape inside layered PowerShell, Git Bash and `bash -lc` quoting lost its backslash before `printf` executed | Confirm no build exists for the exact SHA, then retry once with Bash builtin `echo DEPLOY` in the same attached process | README approval transport guidance names the proven LF relay and warns against unverified multiply quoted `printf` escapes |
| DA-023 | A deployment request reaches a local commit that is not on the configured remote branch, and the caller attempts to push sensitive release data without separately confirming the publication destination | Production deployment approval and source publication approval were treated as the same authority | Stop before push; confirm remote URL, branch, visibility, author, authenticated principal, revision and sensitive-data scope; obtain explicit publication approval, publish through the approved Git workflow, then rerun deployment | Remote-parity failure and project prompt state that the toolkit never pushes and deployment approval does not authorize source publication |
| DA-024 | Preflight starts clean, but the production build rewrites tracked generated files and Cloud Build would upload content different from the commit named by the image tag | Cleanliness was checked only before the build; generators or line-ending conversion changed the submission workspace afterwards | Make the build reproducible, then require the working tree to remain clean after the build before any cloud submission | Preflight performs a second `git status --porcelain` gate immediately after the production build; test fixture proves tracked build mutations fail closed |
| DA-025 | A reviewed text dataset fails its release hash after checkout on another operating system although parsed content is unchanged | The integrity digest included platform-converted CRLF/LF bytes instead of a portable text representation | Keep the immutable source manifest byte-exact, but normalize CRLF to LF when binding generated public text datasets and human-review overrides | Cross-platform release verification tests the same generated text dataset under LF and CRLF checkout conventions |
| DA-026 | The deployment stalls or hangs indefinitely on `Uploading tarball...` before the Cloud Build starts | The workspace contains hundreds of megabytes of scratch files, transcripts, or data dumps that `gcloud` is trying to package | Add `scratch_*`, transcripts, and large local files to `.gcloudignore` | A robust `.gcloudignore` template must be explicitly maintained to exclude heavy local context from the build tarball |
| DA-027 | One agent uses central RA-002 while another follows a stale project-local deploy script with an old region or ad-hoc source-deploy path | The consumer copied the controller and kept active routers/prompts pointing at both owners | Replace the local implementation with a thin adapter that sets the project config and delegates to RA-002; repoint every active router and prompt; keep the old plan historical only | RA-002 setup forbids competing full copies and requires an adoption search for stale paths, hard-coded regions and ad-hoc deployment commands |
| DA-028 | RA-002 starts under an explicitly invoked Windows `bash.exe` but later reports standard utilities such as `dirname` or `sed` missing | PowerShell launched Git Bash without Git's `/usr/bin` and `/bin` entries in `PATH` | Restore `/usr/bin:/bin` at controller startup while preserving the caller's remaining tool paths | `deploy.sh` initializes the Git Bash utility path before argument parsing or preflight |
| DA-029 | Secret Manager receives a zero-filled encryption key even though the operator attempted to use a cryptographic RNG | Windows PowerShell's installed .NET runtime lacked the static `RandomNumberGenerator.Fill` method, and the non-terminating method error allowed the pipeline to continue with the initialized zero buffer | Destroy the invalid version before deployment; generate a replacement with `RandomNumberGenerator.Create().GetBytes`; set `$ErrorActionPreference='Stop'`; verify only decoded byte count and nonconstant bytes without printing the secret; pin the verified version | README secret-bootstrap safety gate forbids `Fill`, requires fail-closed PowerShell, in-memory generation, non-disclosing verification and explicit secret-version pinning |

| DA-030 | Final handover reports an older commit, Cloud Run revision, traffic, image, test count or superseded issue diagnosis after concurrent agent work | Report facts were copied from earlier in the session instead of re-reading Git, live Cloud Run, the current test command and the canonical issue log | Re-query Git and Cloud Run at handover; print `REPORT RECONCILE: STALE` and fail if they moved; agents must use the latest block, current tests and issue log | Handover reconcile gate plus project prompt forbids memory-copied release facts |
| DA-031 | Staging succeeds but production cannot pull the same cross-project image before traffic changes | Preflight verified repository existence and runtime/build identities, but omitted the production Cloud Run service agent | Separately authorize repository-scoped Artifact Registry Reader for the affected service agent, verify effective access, then retry the same image | `cloud-run-image-access.mjs` checks both target service agents' effective `downloadArtifacts` access; consumer isolation-hook integration runs it before build/promotion and rejects denied, unknown or failed queries |
| DA-032 | The same container digest passes staging but its browser connects to production data | Public Firebase/API project values were compiled into the JavaScript bundle while the server used ambient runtime credentials | Move browser environment selection to runtime-injected public configuration; require separate projects, identities and data-boundary identifiers | Staged-release preflight rejects shared projects/identities, and the consumer proves one digest against both runtime profiles |
| DA-033 | A receipt names the right digest but promotion selects a newer build/revision or the first traffic entry | Mutable `latest` queries and `status.traffic[0]` were treated as authoritative under concurrent releases or traffic splits | Bind the exact Build ID, deterministic revision and digest; parse the complete traffic array and re-query those exact resources before promotion | Receipt helper tests reordered traffic; controller never selects a latest build/revision for staged promotion |
| DA-034 | Production receives an untested rebuild or a candidate gets traffic before verification | Build, deploy and traffic movement were coupled in one pipeline | Build exactly once, deploy digest-tagged candidates with zero traffic, smoke the tagged URL, then route traffic to the exact revision behind a separate production gate | Stub suite asserts one build, `@sha256`, `--no-traffic`, exact-revision traffic and zero build submissions during promotion |
| DA-035 | A nominally isolated staging gate can create build state in production, miss effective inherited IAM, trust environment-looking Firebase values, lose origin-scoped authentication, trust a tampered receipt or become unrecoverable after interruption | Release and production shared a project; direct IAM, nonempty config, per-commit browser origins, YAML scanning, writable receipts and zero-traffic-only retry assumptions were treated as sufficient boundaries | Require three projects and a dedicated artifact-only build identity; use an effective-IAM consumer verifier and authoritative environment config; smoke the tag but run authentication on a stable exact-revision service origin; atomically create strict receipts; resume the exact Build ID and deterministic revision | Staged-release tests cover three-project isolation, correct repository selection, stable-origin verification, dedicated build identity, tag binding, strict immutable receipts, interrupted-stage reconciliation and no-rebuild promotion |
| DA-036 | A Node-based prerequisite verifier passes unit tests but cannot launch `gcloud` on Windows or receives a Firebase API quota-project rejection | Node does not resolve the installed Cloud SDK batch shim like a shell, and user-token Firebase Management calls omit quota attribution | Invoke the installed `gcloud.ps1` through PowerShell with an argument array and no command shell; independently bind the resource URL to the target project, then use `x-goog-user-project` only for quota/billing with pre-existing `serviceusage.services.use` | Portable helper tests cover non-Windows, Windows paths/arguments, unsafe-option rejection, fail-closed execution and Firebase quota headers; the consuming project must also pass a live read-only staging check |
