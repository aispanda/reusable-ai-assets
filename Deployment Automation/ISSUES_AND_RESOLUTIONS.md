# Deployment issues and resolutions

Record reusable root causes only. A resolution is complete when its prevention step is incorporated into the workflow or release checklist.

| ID | Symptom | Root cause | Resolution | Prevention |
|---|---|---|---|---|
| DA-001 | First release cannot build, push or resolve a service URL | Repeat-release assumptions hid missing APIs, image repository and service | Classify first deployment; verify billing/APIs/repository; resolve the runtime URL after deployment | Preflight checks first-deployment readiness before mutation |
| DA-002 | Local build passes but clean cloud container install rejects a dependency-age rule | The Docker install layer did not include the package-manager policy file | Copy all policy files before dependency installation; retain the rule and exclude only an explicitly reviewed package/version | Container review compares local and install-layer policy inputs |
| DA-003 | CLI default project differs from deployment target | Shared workstation retained another project's default | Pass the target project explicitly on every cloud command and show the mismatch as a warning | Preflight verifies access and billing against the configured target, not the global default |
| DA-004 | Deployment succeeds but the public URL returns 403 | The build principal created the service but could not apply unauthenticated invocation | Apply the approved public/private access policy with an authorised principal, then verify anonymously | Treat access mode as a separate release gate and test without credentials |
| DA-005 | Verifier reports failure although build, image digest and serving revision are correct | It depended on one legacy console phrase that newer builders omit | Treat log wording as diagnostic; verify build status, immutable registry digest, revision digest and traffic through APIs | Never use mutable console text as authoritative release evidence |
| DA-006 | A newly public healthy service returns one transient 503 during verification | First-request platform or instance readiness briefly lagged the ready control-plane state | Retry only transient HTTP failures with a small bounded delay, then fail loudly | Public-route checks use two bounded retries and still require final HTTP 200 |
| DA-007 | Custom domain work drifts toward ALB “because Google recommends it” and burns ~$18+/mo | Production guidance defaults to load balancer without a zero-cost mandate | Library policy: Cloud Run domain mapping only; ALB forbidden unless CD-B2 trigger + explicit cost acceptance | `CUSTOM_DOMAIN.md` policy table + `domain_map.sh` warns; backlog CD-B2 |
| DA-008 | Agents propose Firebase Hosting as domain front-door | Older docs list Firebase as a mapping option | Firebase proxy excluded by default (past delivery friction) | `CUSTOM_DOMAIN.md` forbidden list; backlog CD-B3 only if Firebase already mandated |
| DA-009 | Operators invent DNS records instead of using Google’s mapping output | Registrar UI is filled before `domain-mappings describe` | Always `--export-dns` → plan JSON → registrar apply | `export_dns_records.py` + `apply_dns.py`; never hand-author rrdata |
| DA-010 | Spaceship API DNS apply fails with auth/forbidden despite valid keys | API Manager IP allowlist does not include the agent/runner egress IP | Use `--provider manual` (UI paste from exported plan) until the IP is allowlisted; then retry API | Default DNS path is UI paste; document IP allowlist in `CUSTOM_DOMAIN.md` before recommending API |
| DA-011 | Only `www` or only apex is mapped; the other URL fails for visitors | Assumed one hostname is enough | Map **both** by default; set canonical to `www` | Defaults table in `CUSTOM_DOMAIN.md`; `CUSTOM_DOMAIN_HOSTS` lists both |
| DA-012 | `domain-mappings create` rejects hostname: domain not verified for account | Cloud Run mapping requires prior domain ownership proof (Search Console / `gcloud domains verify`) | Run `gcloud domains verify <apex>`; publish the TXT (or other) challenge at the registrar; re-run `--map` | Add ownership-verify as step 0 before `--map`; export challenge for UI paste |
| DA-013 | Exported mapping JSON on Windows is UTF-16 and breaks UTF-8 parsers | PowerShell `>` / default `Out-File` writes Unicode | Write plans via Python/`cmd` redirection or decode `utf-16`/`utf-8-sig` in exporters | `export_dns_records.py` should tolerate UTF-16 BOM when reading gcloud capture files |
| DA-014 | DNS correct and DomainRoutable but HTTPS fails briefly | Managed certificate still `CertificatePending` (minutes–hours) | Do not change mapping records; poll `domain-mappings describe` until Ready; keep `*.run.app` as fallback | After UI paste, treat cert wait as normal; only escalate if pending >24h with correct public DNS |
| DA-015 | Cert stays pending: “challenge data was not visible through the public internet” while public A/CNAME already match Google | Propagation lag, intermittent checker path, or registrar edge cache; Google lengthens retry (e.g. 15m) | Confirm NS + A/AAAA/CNAME via 8.8.8.8 and 1.1.1.1; do **not** rewrite correct records; wait for Retry; escalate only if still failing after several successful public resolutions and >2h | Document challenge-not-visible as wait/retry, not a signal to invent different IPs |
| DA-016 | Deploy succeeds but INFRA VERIFY fails with curl exit 28 / host`:8080` on Windows Git Bash | MSYS path conversion rewrites `https://…/route` during verify even when `MSYS2_ARG_CONV_EXCL` lists http/https | Call `curl.exe` when present; otherwise force `MSYS_NO_PATHCONV=1` and `MSYS2_ARG_CONV_EXCL='*'` for curl | `run_curl` in `deploy.sh` prefers `curl.exe` |
| DA-017 | Agent keeps re-asking the user to type `DEPLOY` after they already approved in the chat | Approval channel treated as “new terminal only” | Accept exact chat `DEPLOY` once for that SHA and relay LF-only stdin; do not ask again for the same release | `DEPLOY_PROJECT_PROMPT.md` one-approval rule |
| DA-018 | Windows operators cannot start the documented command because `bash` is not on PowerShell `PATH` even though Git Bash is installed | The operating guide assumed a POSIX shell command alias was globally available | Invoke the installed Git Bash executable explicitly and continue using the existing Windows path conversion | README includes the explicit Windows invocation fallback |
| DA-019 | The RA-002 test suite passes preflight gates, then exits during standalone verification on Windows | `deploy.sh` correctly prefers `curl.exe`, but the test fixture stubbed only `curl`, allowing the real network client to escape the isolated test | Create matching `curl` and `curl.exe` stubs in the temporary fixture | The test now proves native curl preference without making a network call |
| DA-020 | A caller reports a deployment timeout even though Cloud Build continues and succeeds | The calling tool allowed less time than combined preflight, upload, build, rollout and verification | Use a foreground timeout of at least 15 minutes; if the caller still exits after submission, reconcile the exact SHA in Cloud Build and Cloud Run before retrying | README retry safety requires sufficient caller time and exact SHA reconciliation after interrupted output |
